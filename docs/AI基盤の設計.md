# AI 基盤の設計（叩き台 v0.1）

> **2026-11-09 の決め（実装の前提）**: 書き方は **2 層改**（記録から直接欄の値を書き、作り話を抑える 4 つの工夫を足す。比べた結果は手元の runner の README）にした。実装は `worker/vertex/`。そのため、この文書の「事実（2 層目）」「確かめること」「ケアマネの直しを judge の事実にする」「見直しの候補（proposals）」「書き込みの元に戻す」は、今の実装では作っていない。DB と API の今の形は [`DB設計.md`](DB設計.md)・[`API設計.md`](API設計.md)。

録音や書類の写しから、アセスメントなどの書類を書く AI の仕組み。2026-11-08 作成。チームで直す前提の叩き台。

- 元にしたもの: メンバーの「介護支援 AI：LangChain・AI 基盤 設計提案書」（2026-11-07）。良いところは残した。11-08 に決めたこと（データの 3 層、用紙の上で直す画面、チャットのエージェント、シートでの採点）に合わせて組み直した。何を変えたかは 2 章。
- 関係する決めごと: [`データの定義.md`](データの定義.md)（3 層のデータ）、[`fields.json`](../core/fields.json)（欄の一覧。296 欄）、[`scenario/`](../eval/scenario/README.md)（テストの入力と正解）、[`bench/`](../eval/bench/README.md)（採点）、[`pdfme/`](../forms/README.md)（PDF）。
- 画面のデザインは別にある。ここには、画面との約束（何を渡すか）だけを書く。

## 1. 要点

1. **録音の処理は決まった流れ、チャットはエージェント。** 録音や書類が届いたら、決まった順番で処理して用紙に書く（毎回同じ動きなので、採点して直しやすい）。ケアマネとのチャットでは、AI が道具（ツール）を選んで使う。道具の中身は、録音の処理と同じ関数。
2. **データは 3 層（原本・事実・シート）。** AI が返すのは、事実と、欄の値（fields.json の key と、型どおりの値）だけ。✓ や ○ の位置は扱わない。位置は pdfme の変換が決まった手順で作る。
3. **AI は用紙にそのまま書く。欄ごとの承認はない。** その代わり、書いたら必ず差分（− 前／＋ 今）をチャットに出す。1 回の書き込みは、まとめて元に戻せる。ケアマネが書いた欄・直した欄は、AI が勝手に書き換えない。AI が書いた値は、ケアマネが保存したあとでも、新しい話が出れば書き換える（2026-11-08 に決めた。13 章）。
4. **確定は「保存」。** 保存のたびに版を残す。PDF や介護ソフトへの出力は、保存した版から作る。AI が書いただけで、まだ保存していない値は外に出ない。AI は保存できない。
5. **評価は bench（シートが主）。** 最初に、`eval/scenario/原本.json` から 1 回目・2 回目の提出を作るコマンドを作る。採点しながら直す。
6. **欄は fields.json の key をそのまま使う。** 296 欄。アセスメントの必須は `required.assess` の 84。選択肢と型も、fields.json から作ったスキーマで確かめる。

## 2. 提案書（11/7）から変えたところ

| 項目 | 提案書 | この設計 | 理由 |
|---|---|---|---|
| エージェント | 決まった流れだけ。AI がツールを選ぶ形は使わない | 録音の処理は決まった流れ。チャットはツールを使うエージェント（7 章） | プロダクトは「AI 業務エージェント」。「足りないところは？」「合わないところは？」「入院時情報提供書を作って」に答えるには、AI が自分で用紙や事実を読みに行く必要がある。データの定義でも、会話では「事実を探す」道具を持たせると決めている |
| 事実の持ち方 | 事実に fieldId を付ける | 事実には 23 項目の番号・誰の情報か・種類（言った・見た・書類・判断）を付ける。どの欄に置くかは次の段で決める | 同じ事実を別の書類でも使うため。欄に直接付けると様式に縛られる（データの定義の 3 層） |
| 事実の統合 | `mergeFacts`（new／duplicate／supplement／conflict／needs_review） | 事実はまとめない。同じことを別の日に言っても 2 件のまま。食い違いも並べて持つ | いつ・誰が言ったかが違うため。まとめる段をなくすと AI の判断が 1 つ減り、間違える場所も減る。まとめは、欄の値を書く段で行う |
| 承認 | 書類ごと・版ごとに承認。追加の録音は「更新候補あり」→ ケアマネが指示 → v2 の下書き → 再承認 | AI がそのまま用紙に書く。ケアマネは違うところだけ直して保存。書いた中身は、差分と「元に戻す」で見えるようにする | 画面の決めごと（欄ごとの承認はしない、録音を止めると AI が書く）。年配のケアマネに、承認の操作を増やさない |
| 評価 | 抽出の Precision・Recall が主 | bench のシートの採点が主。事実（2 層目）は、どこで落ちたかを見るのに使う | 大事なのは「聞いた話がシートに正しく書けているか」（データの定義、scenario の決めごと） |
| 欄の定義 | フィールド定義担当に頼む | `fields.json` がもうある（296 欄、型、選択肢、23 項目の番号、出どころ、様式での置き場所） | — |
| 複数の録音 | 同じ日の追加録音。P2（余力があれば） | 日をまたぐ面談（1/21 病院、1/25 家屋調査）が中心。最初から作る | シナリオも正解も 2 回分（v1・v2）。デモの中心 |
| 話した人 | 本人・家族・ケアマネ | 原本の `people`（立場は本人・家族・専門職・ケアマネ。ほかに続柄・職種）。利用者ごとに覚えておく | シナリオに看護師・PT・OT・ST・MSW が出てくる |
| 値の型 | 文字列の簡略形。型は未確定 | fields.json の型（enum・multi・bool・object・list など）どおりの値。zod で確かめる | 用紙は ✓ と ○ がほとんど。型が決まらないと PDF が出せない |
| 用紙を止める時間 | — | 書く中身は「文字起こし中」の間に作っておく。用紙を止めるのは、反映する数秒だけ | 画面では 30 秒ほどとしていたが、もっと短くできる。画面と操作は変わらない（「AI が書き込み中」が短くなるだけ） |
| 書類の名前 | 入院時情報連携シート | 入院時情報提供書 | pdfme の様式（地域の連携会議の版、2018.10）に合わせた |

**そのまま残したところ**

- AI は候補を返すだけ。ID・日時・誰が書いたかは、プログラムが付ける。
- 根拠をプログラムで確かめる（元の発言の ID があるか、引用がその発言に含まれるか）。
- 根拠のないことは書かない。「話に出ていない」と「否定した」を分ける。
- 食い違う話は両方残す。録音の順番で上書きしない。
- 一部が失敗しても、通った分で進める。失敗した段からやり直す。ジョブ ID で同じ処理を 2 回しない。
- 個人情報をログに出さない。音声と PDF は非公開の置き場に置く。AI の処理は API と別のサービスにする。
- TypeScript + LangChain + Gemini（Vertex AI）。PostgreSQL・Cloud Storage・Cloud Tasks・Cloud Run の構成（細かいところはバックエンド担当が決める）。
- AI は PDF の座標やレイアウトに触らない。
- 出力には、モデル・プロンプト・fields.json の版を付けて残す。

## 3. 全体の流れ

```
iPad・PC
  │ 録音、書類の写し、チャットのメモ
  ▼
API（受け付け、保存、ジョブを積む）
  │
  ▼
AI の処理（Cloud Run、API とは別のサービス）
  ① 文字にする（STT）          ─┐
  ② 話した人を決める             │ → 原本（1 層目）
  ③ 事実を取り出す               │ → 事実（2 層目）、確かめること
  ④ 根拠を確かめる               │
  ⑤ 置き場所を決める             │
  ⑥ 欄の値を作る                 │   ここまで、用紙は書ける
  ⑦ 値を確かめる               ─┘
  ⑧ 用紙に反映する（数秒だけ用紙を止める） → 書き込み（差分）、シート（3 層目）
  ⑨ チャットに作業ログと差分を出す

PC のチャット
  ケアマネ ⇄ エージェント（道具: 用紙を読む、事実を探す、用紙に書く、書類を作る、聞く …）
  用紙を変える道具は、⑧ と同じ入口を通る

保存 → 版 → PDF（pdfme）、介護ソフトへの出力
```

画面の状態との対応（iPad で録音したとき）:

| 画面の状態 | 処理 | 用紙 |
|---|---|---|
| 録音中 | — | 書ける |
| 送っています | 音声のアップロード | 書ける。送り終わるまで iPad を閉じない |
| 文字起こし中 | ①〜⑦（いちばん長い） | 書ける。iPad を閉じてよい |
| AI が書き込み中 | ⑧ | 止める（数秒） |
| 書き終わり | ⑨ | 書ける |

用紙を変える入口は ⑧ の `applyBatch` 1 つだけにする。録音の処理もチャットも、ここを通る。同じ書類に 2 つの書き込みを同時に入れない。

## 4. データ

3 層（原本・事実・シート）と「確かめること」は [`データの定義.md`](データの定義.md) のとおり。ここでは、それに足すものを書く。

### 4.1 シートの欄（3 層目に足すもの）

例は演習シナリオの「住居の特記」。1 回目（1/21）に AI が書き、2 回目（1/25 の家屋調査）で書き足した状態。

```json
"housing.notes": {
  "value": "家の中はバリアフリーに改築してある。カーペットや座布団などのちょっとした段差に注意が要る（OT）。手すりや段差解消などの住宅改修は要らない",
  "by": "ai",
  "facts": ["f-022a", "f-025c", "f-s3-004"],
  "batch": "b-2",
  "updatedAt": "2021-01-25T17:05:00+09:00",
  "history": [
    {"value": "家の中はバリアフリーに改築してある。カーペットや座布団などのちょっとした段差に注意が要る（OT）",
     "by": "ai", "batch": "b-1", "at": "2021-01-21T18:10:00+09:00"}
  ]
}
```

| 属性 | 意味 |
|---|---|
| `by` | 今の値を書いたのは誰か。`ai`／`cm`（ケアマネ）。AI が書き換えてよいかは、これで決まる（6 章） |
| `facts` | 根拠の事実（データの定義と同じ） |
| `batch` | 最後にこの欄を書いた書き込みの番号。元に戻すときに使う |
| `history` | 前の値。書き換えるたびに足す。入院時の書類で「入院前の状態」を出すときにも使う |

データの定義 v0.2 の `status`（empty／proposed／confirmed）はやめ、`by` と「保存した版に入っているか」で表す（データの定義 v0.3 で直した）。bench の採点は `status` を使っていない。

### 4.2 書き込み

1 回の録音・書類・チャットの頼みで、AI が用紙を変えたまとまり。差分の表示と、元に戻すの単位になる。上の例の 2 回目は次のようになる。

```json
{
  "id": "b-2",
  "document": "assessment",
  "trigger": {"type": "recording", "id": "rec-0125"},
  "changes": [
    {"key": "housing.bedding", "op": "add", "before": null, "after": "ベッド", "facts": ["f-s3-002b"]},
    {"key": "housing.mobilityAidsIndoor", "op": "add", "before": null, "after": ["杖"], "facts": ["f-s3-001"]},
    {"key": "housing.notes", "op": "update",
     "before": "家の中はバリアフリーに改築してある。…注意が要る（OT）",
     "after": "家の中はバリアフリーに改築してある。…注意が要る（OT）。手すりや段差解消などの住宅改修は要らない",
     "facts": ["f-s3-004"]},
    {"key": "notes.bath", "op": "update", "before": "…", "after": "…。浴室にシャワーチェアを置けば、介助や見守りのもとで安全に入浴できる",
     "facts": ["f-s3-003"]},
    {"key": "notes.basicMovement", "op": "update", "before": "…",
     "after": "…。自宅では、居室〜台所〜トイレ〜居間を、伝い歩きや4点杖で歩ける。自宅のベッドで寝起きでき、大変なら置き型手すりを置く",
     "facts": ["f-s3-001", "f-s3-002a", "f-s3-002c"]}
  ],
  "kept": [
    {"key": "family.members", "reason": "cm"}
  ],
  "proposals": [],
  "createdAt": "2021-01-25T17:05:00+09:00"
}
```

| 属性 | 意味 |
|---|---|
| `changes` | 書いた欄。`op` は `add`（空だった欄に書いた）か `update`（AI の値を書き換えた） |
| `before` | 前の値。**AI に書かせず、反映する瞬間の用紙からプログラムが取る**（前の値を作り話にさせない） |
| `kept` | 新しい事実があったが、ケアマネの欄なので書き換えなかった欄 |
| `proposals` | ケアマネの欄に、食い違う新しい事実が来たときの案。チャットに「見直しの候補」として出す。書き換えるのは、ケアマネがボタンを押したときだけ |

**元に戻す**: 各欄が今も `after` のままなら、`before` に戻す。書き込みのあとでケアマネが直した欄は戻さず、そう伝える。

### 4.3 版（保存）

ケアマネが保存するたびに、その書類の全部の欄の値を版として残す。版は書き換えない。

```json
{"document": "assessment", "rev": 3, "savedBy": "加藤", "savedAt": "2021-01-25T18:00:00+09:00", "values": {"…": "…"}}
```

- PDF・介護ソフトへの出力（CSV など）は、版から作る。
- 画面の印は、前の版からの変化として出す。橙は AI が書いた欄、黄はケアマネが直した欄。保存すると消える。誰が書いたかは `by` に残る。

### 4.4 利用者ごとに覚えること

- **話した人**（`people`）: 原本.json の `people` と同じ形（立場、続柄、職種）。次の録音でも使う（同じ嫁が出てきたら同じ人にする）。
- **基本情報の 6 欄**: `person.name`・`person.birthDate`・`person.age`・`person.postalCode`・`person.address`・`person.phone`。書類をまたいで 1 つの値として持つ。どの書類で直しても、全部の書類に入る。

### 4.5 書類

- 書類 = 様式（`assessment`、`admission`、あとで `monitoring` など）と、欄の値の組。どの欄が入るかは fields.json の `forms` で決まる。
- 入院時情報提供書を作るときは、アセスメントに値がある欄を写す。写したあとは別の値として持つ（その時点の、入院前の状態を残すため）。基本情報の 6 欄だけは、つながったまま。

## 5. 録音の処理（決まった流れ）

| 段 | 関数 | 入力 | 出力 | 使うもの |
|---|---|---|---|---|
| ① 文字にする | `transcribe` | 音声 | 発言（id・時刻・話者の記号・文） | STT |
| ② 話した人を決める | `assignSpeakers` | 発言、利用者の `people` | 話者の記号 → 人 | Gemini 1 回 |
| ③ 事実を取り出す | `extractFacts` | 発言（区切りごと）、開いている確かめること | 事実、確かめること（新しいもの・閉じたもの） | Gemini（区切りごとに並べて呼ぶ） |
| ④ 根拠を確かめる | `validateFacts` | 事実、原本 | 通った事実、落とした事実と理由 | プログラム |
| ⑤ 置き場所を決める | `placeFacts` | 新しい事実、同じ番号の欄の候補 | 事実 → 欄、または「入れる欄がない」 | Gemini（23 項目ごとに並べて呼ぶ） |
| ⑥ 欄の値を作る | `draftValues` | 欄ごとの事実（前回までの分も）、今の値と `by` | 欄の値 | Gemini（23 項目ごとに並べて呼ぶ） |
| ⑦ 値を確かめる | `validateValues` | 値、fields.json | 通った値、落とした値 | プログラム（zod） |
| ⑧ 用紙に反映する | `applyBatch` | 値、今の用紙 | 書き込み（差分） | プログラム |
| ⑨ チャットに出す | `postLog` | 各段の結果、書き込み | 作業ログと差分 | プログラム |

① の STT と書類の写しの読み取りのほかに、Gemini を使うのは ②③⑤⑥ だけ。ほかはプログラムで、毎回同じに動く。

### ① 文字にする

- 受け取る形は、提案書の 4.1 をそのまま使う（`recordingId`、発言ごとの `segmentId`・`speakerId`・`startMs`・`endMs`・`text`）。
- 原本の発言 id は `<録音の番号>-<連番>`（例 `r2-0153`）にして、録音をまたいでも重ならないようにする。
- STT の道具は STT 担当が決める（Google の Speech-to-Text と Gemini の音声入力を比べる）。日本語の話者分けがどこまでできるかを、最初に確かめる。
- **書類の写し**（被保険者証、認定調査票、主治医意見書など）は、① の代わりに Gemini で文字と表を読み、原本の「書類」の場面にする。そこからの事実は `kind: "doc"`。認定調査票があれば、用紙の 6 章（5〜9 ページ）の多くが会話より正確に埋まる（データの定義の「作ってみて分かったこと」2）。
- **チャットに書かれたメモ**も原本に入れる（場面は「メモ」、書いた人はケアマネ）。

### ② 話した人を決める

- 話者の記号（`speaker_1` など）は録音ごとに振り直される。利用者の `people` と話の中身（呼び方、職種の名乗り、話していること）から、誰かを決める。
- 新しく出てきた人（例: 初めて出てきた OT）は `people` に足す。
- 決められない話者は「不明」のまま進める。その人の事実は `who` を空にする。チャットで「話者 3 は春子さんですか」と聞くかは、まだ決めていない（14 章）。
- bench（原本.json）では `people` が決まっているので、② を飛ばす。② の正しさは別に測る。

### ③ 事実を取り出す

- 1 件 = 1 つの事実。23 項目の番号を 1 つ付ける（データの定義の決まり）。
- 出力には、元の発言からの短い抜き出し（`quote`）を必ず付けさせる。④ で、`from` の発言にその文字列が含まれるかを確かめる（提案書の「引用一致」）。
- 区切り: 場面ごとに分け、長い場面は 10 分ほどで分けて並べて呼ぶ。境目は前後を少し重ねる。重ねた所で同じ事実が 2 回出たら、`from` と文が同じものを 1 つにする（これは同じ録音の中の重なりの片付けで、日をまたぐ統合ではない）。
- 開いている「確かめること」も一緒に渡す。答えが出たら閉じ（`closedBy`）、新しく出たものは足す。確かめることはチャットに一覧として出さない（2026-11-08）。「足りないところは？」と聞かれたときの答えと、聞き取りの提案に使う。
- 事実にしないもの: 推測（確かめることに入れる）、制度や契約の説明（シナリオの `s1`）、ト書き。

出力の形（Gemini が返すもの）:

```json
{
  "facts": [
    {"text": "咀嚼に大きな問題はない", "item23": 19, "who": "ST", "kind": "said",
     "from": ["s2-031"], "quote": "咀嚼、嚥下については大きな問題は見られません", "when": null}
  ],
  "questions": [
    {"text": "自宅のカーペット・絨毯・座布団などの段差", "item23": 22, "why": "later", "from": ["s2-025"]}
  ],
  "closed": [
    {"question": "q-002", "by": ["s3-004"]}
  ]
}
```

（`quote` は、原本の `s2-031`（ST の発言）にそのまま含まれる文字列）

### ④ 根拠を確かめる（プログラム）

- `from` の id があり、今回の録音の発言であること。`quote` がその発言に含まれること（全角・半角と空白はそろえてから比べる）。
- `who` が `people` にいること。`item23` が 1〜23 であること。`kind` が 4 つ（said・seen・doc・judge）のどれかであること。
- 落とした事実は、理由と一緒に数えて残す（作業ログの中で見られる）。

### ⑤ 置き場所を決める

- 欄の候補は、fields.json で同じ `item23` を持ち、その書類の `forms` にある欄。
- 決まり: 1 つの事実を文章で書くのは、1 つの欄だけ。置き場所の決まりは [`scenario/README.md`](../eval/scenario/README.md) の表。選ぶ欄や表の欄には、文章の欄とは別に入れてよい。
- どこにも入らない事実は「入れる欄がない」（`unplaced`）にする。全部の事実が、どこかに置かれたか `unplaced` かを確かめる（データの定義の「漏れの確かめ」）。
- 置き場所（⑤）と値（⑥）を分けるのは、⑥ で欄ごとに、その欄に置いた事実だけを渡すため。こうすると、根拠にないことを書きにくくなり、どの事実から書いたかがはっきりする。

### ⑥ 欄の値を作る

**AI が書く欄**は、fields.json の `source`（出どころ）で決まる。

| `source` | 扱い |
|---|---|
| `talk`（会話）、`doc:…`（書類） | 置いた事実があれば、AI が書く |
| `draft`（全体のまとめなど） | ほかの欄を書いたあとに、シートから案を書く |
| `derived`（年齢など） | プログラムが計算する |
| `judge` だけ（ケアマネの判断） | 書かない。チャットで聞かれたら、候補と理由を言う |
| `setting`（事業所の情報）、`event`（書類を作るときに聞く） | 書かない。設定から入れるか、書類を作るときに聞く |

**書き方の決まり**

- 渡すもの: 欄の定義（label・型・選択肢・note）、その欄に置いた事実（前回までの分も）、今の値と `by`。
- 新しい事実が置かれた欄だけを作り直す。中身が同じなら、今の文を変えない（言い回しだけの書き換えで、差分を増やさない）。プログラムでも、前と同じ値なら書き込みに入れない。
- `by: "cm"` の欄は作り直さない。ただし、新しい事実が今の値と食い違うときは、案を作って `proposals` に入れる。
- 食い違う事実は、文章の欄には両方書く（例:「口の左側に食べ物が残ることがある（ST）。本人は気にならないと言う」）。選ぶ欄では、新しい方の事実を選ぶ。同じ時点の食い違いなら、専門職の見立てを選ぶ。どちらにしたかは、作業ログの中に残す。
- AI は欄を空にしない。話に出ていないことは、空のままにする（作り話にしない）。

### ⑦ 値を確かめる（プログラム）

- fields.json から zod のスキーマを作る。enum は選択肢のどれか、multi は選択肢の配列、bool、date（西暦で持つ）、number、object（`types` の形。例: `HasDetail`）、list（行の形）。
- 通らない値は落として数える。

値の例（型ごと）:

```json
{
  "meal.chewing": "問題なし",
  "survey.1_7": "何かにつかまればできる",
  "housing.mobilityAidsIndoor": ["杖"],
  "communication.speechDisorder": {"has": true, "detail": "ろれつが回りにくく、言葉が出にくい。ゆっくり話せば日常の意思疎通はできる"},
  "family.members": [{"relationship": "子の配偶者", "isMainCaregiver": true}]
}
```

形は bench の提出の形（`bench/README.md` の「提出の形」）と同じにする。

### ⑧ 用紙に反映する（プログラム）

1. 用紙を止める。
2. 今の用紙を読み直す（②〜⑦ の間に、ケアマネが直した欄があるかもしれない）。
3. 6 章の決まりで書く。`before` はここで取る。
4. 書き込みと、欄の `history` を保存する。
5. 用紙を戻す。

②〜⑦ は用紙を止めずに行う。その間にケアマネが直した欄は、2. の時点で `by: "cm"` になっているので書かない。だから、用紙を止めるのは反映の数秒だけで済む。

### ⑨ チャットに出す（プログラム）

- 作業ログは、段ごとに 1 行。例: 「録音を文字にした — 42 分・話した人 6 人」「話を事実に分けた — 72 件」「用紙を読んだ — 加藤さんが書いた 3 欄は残す」「用紙に書いた — 書き換え 2・新しく 2」。押すと中身が見られる。
- 「用紙に書いた」の中身は差分（8 章）。
- 文は AI に作らせない。決まった文に数を入れる（毎回同じ言い方で、間違えない）。

## 6. 書き換えの決まり

| 欄の今の値 | 録音・書類のあと（自動） | チャットで頼まれたとき |
|---|---|---|
| 空 | 書く。差分は ＋ だけ | 書く |
| AI が書いた（保存の前でも後でも） | 新しい事実があれば書き換える。差分は − と ＋ | 書き換える |
| ケアマネが書いた・直した | 書き換えない。食い違う新しい事実が来たら、チャットに「見直しの候補」として差分を出す。ボタン 1 つで書き換えられる | 書き換える（頼まれたため）。値はケアマネの欄として持つ |

- ケアマネが用紙で直した値は、2 層目に `kind: "judge"` の事実として入れる（データの定義の決まり）。チャットで頼まれて書いた値も同じで、根拠は頼んだメッセージになる。
- AI が書いた値は、ケアマネが保存したあとでも書き換える（2026-11-08 に決めた。理由は 13 章）。

## 7. チャットのエージェント

### 7.1 道具

| 道具 | 名前（コード） | すること | 用紙を変えるか | 作業ログの 1 行の例 |

**持たせない道具**: 保存、PDF を出す、外に送る、書類を消す。確定と外に出すことは、ケアマネが画面で行う。

### 7.2 決まり（システムプロンプトに書くこと）

- 用紙について答えるときは、先に用紙と事実を読む。覚えているつもりで答えない。
- 根拠のないことは書かない。書くときは、事実かケアマネの頼みを根拠にする。
- 書いたあとの差分は画面が出すので、文では繰り返さない。文は 1〜2 文にする。
- 聞くときは選択肢を付ける（文字を打たずに済むように）。
- 確かめることは一覧にしない。足りないところを聞かれたら、埋め方ごとに分ける。聞き取りが要るものは、1 回の会話で自然に聞ける組にまとめる（例: 家を見ながら聞く — 住まいの種類、部屋の階、トイレの形）。
- ケアマネの判断の欄（fields.json で `judge` だけの欄）は書かない。聞かれたら、候補と理由を言う。
- 1 回の頼みで道具を呼ぶのは 10 回までにする。

### 7.3 用紙を変える道具は、確かめずに実行する

欄ごとの承認はしない（画面の決めごと）。その代わりに、次の 3 つを守る。

- 必ず差分を出す。
- まとめて元に戻せる。
- ケアマネの欄は、頼まれない限り書き換えない。

### 7.4 作り方

- LangChain v1 の `createAgent` に道具を渡す。道具は `tool()` と zod で定義し、中身は 5 章の関数を呼ぶ。
- 画面には `agent.stream(…, { streamMode: "updates" })` で、道具を呼んだ・結果が返った・文、を順に流す（SSE）。作業ログは、この流れから作る。
- モデルは Vertex AI の Gemini。チャットは速さを優先して Flash 系から試す。LangChain から Vertex AI の Gemini を `createAgent` で使えるか（`@langchain/google-vertexai` など）は、最初に確かめる。API の名前は、実装するときに LangChain の docs で確かめる。
- 会話の履歴は利用者ごとに 1 本にする（PC の右の欄）。録音の処理（⑨）の作業ログも、同じ履歴に入れる。そうすると、エージェントが「さっきの録音で何を書いたか」を読める。

### 7.5 例（演習シナリオ）

**「足りないところはどこ？」（1 回目のあと）**

1. `list_missing` → 必須 84 欄のうち、空きは 59。
2. 答え: 「書類の写しで埋まるもの 46（認定調査票・主治医意見書）、被保険者証などで埋まるもの 6、計算で入るもの 2、聞き取りが要るもの 5」。聞き取りの 5 は「家を見ながら」「退院後の過ごし方として」「ご家族に」の組にまとめる。

**「合わないところはない？」**

1. `read_sheet` → `search_facts` → `check_conflicts` で、用紙と事実の食い違いを見つける。
2. 用紙の値と元の話を並べて出す。
3. ケアマネが「直して」と言ったら、`write_fields` で書き、差分を出す。

**「入院時情報提供書を作って」**

1. `create_document`: アセスメントから写せる欄を写し、事実から書ける欄を書く。
2. その場で聞く欄（入院日、医療機関など。`source` が `event`）を `ask_caremanager` で選択肢つきで聞く。
3. 答えを `write_fields` で書く。
4. 書類を開く。

入院時情報提供書の 55 欄の出どころ（データの定義の表）: アセスメントから写す 28、会話 6、その場 18、設定・計算 3。

## 8. 画面に渡すもの（作業ログと差分）

- チャットの 1 回の返事は、作業ログ（道具ごとに 1 行）、文、差分（書き込みがあれば）で作る。
- 作業ログの 1 行は、道具ごとに決まった言い方（7.1 の表）と、結果の数で作る。AI に書かせない。
- 差分は書き込み（4.2）から作る。

| 欄の型 | 差分の出し方 |
|---|---|
| 選ぶ欄（enum・bool・multi） | − 前の選択／＋ 今の選択 |
| 短い文字（text・date・number） | − と ＋ |
| 長い文章（longtext） | 変わった文だけを − と ＋ で出す（文ごとの差分）。全部を出すと長すぎる |
| まとまり（object） | 中の項目ごと |
| 表（list。家族の一覧など） | 足した行・変わった行・消した行 |
| 新しく書いた欄 | ＋ だけ |

- 差分には、欄の名前とページを付ける。発言の時刻や「用紙で見る」は付けない（2026-11-08、使われないため）。
- 書き込みごとに「元に戻す」を付ける。書き換えなかったケアマネの欄は、「書き換えていません」と 1 行で出す。
- 見直しの候補（`proposals`）は、差分に「書き換える」ボタンを付けて出す。

## 9. 評価

### 9.1 主: bench（シートの採点）

AI の処理に、`eval/scenario/原本.json` の 1 回目まで・2 回目までを入力にするコマンドを作る。出力は `<提出>/v1/`・`v2/` の `facts.json`・`questions.json`・`sheet.json`（`bench/README.md` の「提出の形」）。

```sh
# コマンドの名前は例
pnpm bench:submit --source design/scenario/原本.json --out out/submit-1109
python3 design/bench/bench.py score --gold design/scenario/gold --submission out/submit-1109
```

- 原本.json は文字起こし済みなので、①（STT）と ②（話した人）を飛ばして ③ から流す。
- 2 回目は、1 回目の結果の上に流す（プロダクトと同じ動き）。
- 見る数:
  - 書くべき欄の正しい数
  - 作り話（0 を目指す）
  - どこで落ちたか（取り出しか、書く段か。番号違い）
  - 宙に浮いた事実
  - 確かめることが 2 回目で閉じたか
- 判定役は `--judge cache` が既定。Claude に判定させるのは、公開・架空のデータ（このシナリオ）だけにする。

### 9.2 書き換えの決まりのテスト（先に書く）

6 章の表と 4.2 の元に戻すは、TypeScript の単体テストで先に固める（TDD）。

- ケアマネの欄は、録音のあとに書き換わらない。
- 元に戻すは、あとでケアマネが直した欄を戻さない。
- 新しい事実がない欄は、書き込みに入らない。
- `judge` だけの欄は、AI が書かない。
- `before` は、反映した瞬間の用紙の値になる。

### 9.3 2 回目で壊さないか

1 回目のあとに数欄をケアマネの欄に書き換えてから、2 回目を流す。そのうえで、次の 2 つを確かめる。

- 書き換えた欄がそのまま残っているか。
- 1 回目に正しかった欄が、2 回目でも正しいか。

### 9.4 チャット

7.5 の 3 つの頼みを決まった入力にして、呼んだ道具と結果を見る（数は少なくてよい）。

### 9.5 速さと費用

段ごとの時間、Gemini の呼び出し回数、トークンを測る。⑧（用紙を止める時間）は数秒以内にする。

精度の数字はまだない。測ってから書く。

## 10. 失敗・やり直し・安全

- 段ごとに結果を保存し、失敗した段からやり直す（STT が済んでいれば ② から）。
- ③⑤⑥ の一部の区切りが失敗しても、通った分で進める。作業ログに「書けなかったところ」を出す。
- 処理の状態は、提案書の `pending`／`processing`／`completed`／`partial`／`failed` を使う。
- ジョブ ID と入力の版で、同じ処理を 2 回しない（Cloud Tasks の再配信に備える）。
- ログには、録音・文字起こし・プロンプトの中身を出さない。出すのは、ジョブ ID、段、時間、エラーの種類、使った量だけ。
- Vertex AI は東京リージョンで使う。送ったデータが学習に使われない設定と契約を確かめる。現場の聞き取りでも、AI を入れるときの一番の壁は安全と個人情報だった。
- 誰が、いつ、直した・保存した・PDF を出したかを残す。
- 本物の面談の記録は、bench の判定役（Claude）など外のサービスに送らない（プロジェクトの決まり）。

## 13. 決めたこと

### AI が書いて、ケアマネが一度保存した値を、あとの面談で AI が書き換えてよいか → よい（案 A、2026-11-08）

**前からの決まり（どちらの案でも同じ）**

- 録音のあと、AI は用紙に直接書く（橙色）。欄ごとの承認はない。ケアマネは違うところだけ直して、保存する。
- 空いている欄には、AI がそのまま書く。
- ケアマネが書いた値・直した値は、AI は書き換えない。
- PDF や介護ソフトに出るのは、ケアマネが保存した内容だけ。

問いは、**AI が書いた値を、ケアマネが直さずに保存したあと**、次の面談で新しい話が出たときの扱い。

**例（演習シナリオ）**

- 1/21 の病院での面談のあと、AI が「入浴の特記」に「病院ではシャワーチェアを使って介助浴をしている。自宅の浴室は普通のユニットバスで、洗い場が手狭」と書いた。ケアマネは直さずに保存した。
- 1/25 の家屋調査で、「浴室にシャワーチェアを置けば、介助や見守りのもとで安全に入浴できる」と分かった。

| | 案 A: AI がそのまま書き足す（採用） | 案 B: 書き換えずに、チャットで聞く |
|---|---|---|
| 用紙 | 入浴の特記に 1 文が足され、橙色になる | 変わらない |
| チャット | 差分（＋ 浴室にシャワーチェアを置けば…）と「元に戻す」 | 同じ差分と「書き換える」ボタン |
| ケアマネの操作 | 用紙を見て、保存する | ボタンを押してから、保存する |
| PDF・介護ソフトに出る内容 | ケアマネが保存するまで変わらない | 同じ |
| 気を付けること | 一度見た値が変わる。橙色と差分で分かり、元に戻せる | ボタンを押し忘れると、新しい話が用紙に入らないまま保存される |
| このシナリオの 2 回目で起きること | 3 欄に書き足す（住居・基本動作・入浴の特記） | 書き換えの候補が 3 件出る |

**案 A にした理由**

- 外に出る記録は、どちらの案でも、ケアマネが保存するまで変わらない。安全さは同じ。
- 案 B では、確かめる操作が「ボタン」と「保存」の 2 回になる。年配のケアマネに操作を増やさない、という画面の方針に合うのは案 A。

**直したもの**: `データの定義.md`（v0.3）の 3 層目の決まり。「承認した欄は、新しい事実が来ても自動では書き換えない」を、「ケアマネが書いた・直した値は書き換えない。AI が書いた値は、保存したあとでも書き換える」にした。

## 14. まだ決めていないこと

- 話した人が決められないときに、チャットで聞くか。
- 選ぶ欄で事実が食い違うときの選び方。今は「新しい方。同じ時点なら専門職の見立て」とし、作業ログに残す。bench の `anyOf` の欄で確かめる。
- ⑤ 置き場所の段の書き漏れ。2026-11-08 にベンチで確かめた（[`runner/README.md`]（手元の design/runner/README.md） の結果）。
  - 取り出せた事実の約 30% で 23 項目の番号が正解と違い、番号で絞ると欄に届かなかった。全部の欄から選ばせても、1 つの事実は 1〜2 欄にしか置かれなかった。正しく書けた欄は、2 層（記録から直接書く）の約半分だった。
  - 置き場所の段をなくし、欄の側から全部の事実を探す形にすると、2 層に近くなる。ただし作り話が増え、2 回目に読むトークンも減らない。
  - 2 層に、作り話を抑える 4 つの工夫（表の列の決まり、読み直し、2 回目は直すだけ、書類から写す欄は書類がないときは書かない）を足すと、作り話は 2 層の 3 分の 1 程度になり（1 回目 29 → 11.5）、正しく書けた欄は 48.5（2 層は 53）だった（2026-11-09。runner の「2 層改」）。読み直しは、7 章の「照らし合わせる」（`check_conflicts`）を、事実ではなく原本に対して行う形でも使える。
  - どの形にするかを決める。
- 長い文章が用紙の枠に入らないときの要約（pdfme の「まだやっていないこと」）。
- 置き場所の決まりを、fields.json にどう持たせるか。
- 事実をどこまで細かく分けるかの目安（データの定義と同じ）。
- Gemini のモデルと費用の上限。bench で比べてから決める（リージョンは東京）。
- モニタリングとデイの体験用紙（様式ができたら、`create_document` で作れる）。
